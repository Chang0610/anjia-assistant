# 生活服务 AI 小程序落地执行计划

版本：V0.1｜依据 PRD V0.3｜用途：首个试点城市的验证与开发排期

## 1 先作三个决定

1. **只选一个试点城市。** 用目标用户数量、官方规则可维护性、区域租金统计可获得性、地图路线和地点覆盖、运营成本五项打分。尚未取得可靠区域租金数据的城市，不承诺“预算匹配区域”功能。
2. **只服务一段明确场景。** 首期聚焦“即将跨城入职、尚未完成搬入”的单人用户。已有住处、宠物等作为条件分支，暂不扩展家庭协同和全国覆盖。
3. **定义试点成功信号。** 用户完成六项建档后，能说清今天先做的 1–3 件事、每项的完成标准，并在 7 天内反馈至少一项真实推进。具体转化门槛先由 20 个访谈或可用性测试校准，不把提议指标当作已验证目标。

## 2 第 1–2 周：验证需求与关键数据

| 工作 | 产出 | 通过条件 |
| --- | --- | --- |
| 访谈 15–20 名近期跨城入职/换工作者 | 真实时间线、漏办事项、现有工具、愿意持续反馈的原因 | 至少区分首次就业和换工作两类典型任务链 |
| 用现有 PPT 做 5–8 次任务走查 | 用户是否理解六项基线、今日任务、区域参考与提醒状态 | 找出无法理解或误解的页面并修订原型 |
| 建立试点城市知识样本 | 20–30 条任务规则、适用条件、官方入口、来源和审核记录 | 每条政策性结论可定位到有效来源 |
| 验证区域数据 | 合租/整租分开的区域租金统计、通勤路线、菜市场/超市/商场地点 | 能用同一口径给出至少 2–3 个区域参考，否则标为数据缺口 |
| 微信能力实机探测 | 小程序主体、类目、备案与隐私流程、外链打开、订阅提醒实验记录 | 在自己的测试账号和真机上跑通关键路径，记录不可用能力 |

访谈不要问“你会不会用这个产品”，请让受访者回顾最近一次搬家：什么时候知道入职日、先做了什么、哪一步返工、漏了什么、用了哪些入口。再让其使用 PPT 原型完成“生成计划、修改日期、查看提醒状态”三件事。

## 3 第 3–4 周：把 PRD 变成开发规格

先定结构化数据和规则，再接大模型。最小数据对象为 `Profile`、`Plan`、`Task`、`Dependency`、`Evidence`、`Entry`、`AreaReference`、`CostEstimate`、`Reminder`，均需版本、地区和更新时间。六项首次基线必须把“搬家一次性预算”与“每月住房预算”分开。

任务模板至少写清：触发条件、是否适用、前置任务、完成条件、日期依据、是否需要官方证据、用户可见说明。排期程序负责倒推日期、预算冲突和依赖校验；AI 负责识别输入、提出补问、生成解释。AI 产出的计划先过结构、来源、日期和范围校验，再给用户确认。

同时制作 120 个评测案例，覆盖 PRD 的 T01–T38 及知识缺失、日期冲突、来源过期、区域仅部分匹配等变体。每个案例同时写出“必须出现的任务”和“绝不能出现的结论”。

## 4 第 5–8 周：按可验证闭环开发

| 顺序 | 交付内容 | 验收重点 |
| --- | --- | --- |
| A 建档与计划 | 六项输入、按需补问、档案确认、计划预览、今日 1–3 项、任务详情 | 缺字段时保留条件式草稿；日期与预算口径正确 |
| B 可信知识 | 试点城市规则库、任务模板、官方入口库、审核与失效状态 | 不拼接虚构网址；不把过期来源写成确定规则 |
| C 租房准备 | 租房完成节点、检查清单、区域参考、费用区间、周边配套 | 不出现具体房源；通勤与月租同时匹配，未知项明确 |
| D 执行闭环 | 任务反馈、日历、站内提醒、微信订阅能力探测、计划重排与版本 | 打开网址不等于完成；已完成记录保留；旧提醒取消 |
| E 运营后台 | 来源更新、入口巡检、问题反馈、知识回滚 | 可停用错误知识并定位受影响计划 |

最小技术链路：微信小程序前端 → 后端 API → 用户/计划数据库、规则与排期服务、知识与入口库、地图/费用数据服务、模型服务、提醒调度。模型只拿任务所需的最少用户信息；计算结果和证据以结构化字段返回，不靠一段自由文本保存计划。

## 5 第 9–10 周：内测与上线门槛

先用 20 个完整案例做内部检查，再邀请约 50 位目标用户进行 2–4 周灰度。记录首次建档完成率、用户能否找到下一步、7 日任务推进率、提醒授权与发送状态、区域数据缺口、人工审核时间、错误结论和入口失效率。

正式开放前，PRD P0 的阻断项必须为零：跨用户数据访问、虚构政策截止、虚假办理成功、错误城市规则、具体房源推荐、无来源区域匹配、重复或错误提醒。订阅消息需要用户主动触发授权，实际可用模板和发送链路要以目标账号真机验证；保存计划不等于已获得微信推送权限。外部网页也需逐一验证可打开方式与备用搜索路径。

## 6 当前最需要落实的资源

| 资源 | 最小负责人 | 尚需确认 |
| --- | --- | --- |
| 产品与用户研究 | 产品经理 | 试点城市、招募 20 名访谈对象、成功指标 |
| 小程序设计与开发 | 设计师 + 小程序工程师 | 微信主体、页面规格、真机测试设备 |
| 后端与 AI | 后端/AI 工程师 | 规则引擎、计划版本、模型服务、评测环境 |
| 知识与地区数据 | 知识运营负责人 | 官方来源、区域租金授权或可用统计、费用口径 |
| 测试与运营 | 测试/运营负责人 | 120 个案例、反馈工单、失效巡检和回滚流程 |

一个人可以先完成第 1–3 周的访谈、城市数据验证和可点击原型；完整 P0 上线则需要有人持续负责知识更新与测试，不能只靠一次模型接入。

## 7 下一步的具体动作

1. 用一页表给 2–3 个候选城市打分，尤其核验区域租金数据的合法来源与合租/整租口径。
2. 用现有 PPT 约 5 名目标用户做走查，记录他们是否理解“搬家预算”和“月租预算”的区别。
3. 把 PRD 的 T01–T38 录入测试用例表，并补齐试点城市的前 20 条任务模板。
4. 用一个真实微信测试主体验证订阅提醒、外部入口及隐私授权，形成可行性记录。
5. 数据、能力与用户验证都通过后再冻结第一版开发范围和发布日期。

## 参考核验入口

- [腾讯位置服务 WebService API](https://lbs.qq.com/service/webService/webServiceGuide/webServiceOverview)：官方列出地点搜索、公交及步骑路线等能力；实际配额、协议和数据使用方式须按申请账号核验。
- [腾讯云：实现小程序订阅消息推送](https://cloud.tencent.com/document/product/1301/103770)：说明用户主动触发订阅授权与发送链路；正式能力须以微信平台当前文档和真机结果为准。
- [腾讯云：小程序和公众号相关的域名配置指南](https://cloud.tencent.com.cn/document/product/1301/100434)：用于验证外部网页嵌入所需的业务域名配置。
- [工业和信息化部：生成式人工智能服务管理暂行办法](https://www.miit.gov.cn/zcfg/qtl/art/2023/art_f4e8f71ae1dc43b0980b962907b7738f.html)：公开服务前应由负责人员核验适用要求，并与隐私、个人信息处理安排一并评审。
